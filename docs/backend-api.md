# Контракт существующего PHP API

Аудит выполнен по исходникам `../../b2b`, без запуска PHP, подключения к БД, запросов к рабочему серверу и изменений бэкенда. Это описание реализованного кода, а не подтверждение работоспособности развернутого сервиса. Указанные ниже номера строк относятся к исходникам на момент аудита.

## Общие правила запросов

- Базовый путь зависит от размещения сервера; далее маршруты указаны относительно каталога `b2b`. Файл `catalog/index.php` соответствует `catalog/` при стандартном `DirectoryIndex`; явный `catalog/index.php` также указывает на этот файл. Файлы `*.php`, например `banner/tovs.php`, сохраняют расширение в маршруте.
- Все прикладные обработчики читают параметры из `$_GET`. Для совместимости запросы выполняются методом **GET**, параметры кодируются через `URLSearchParams`. Заголовок `Access-Control-Allow-Methods: GET, POST` не означает поддержку JSON или POST-тела: чтения `$_POST` / `php://input` в этих файлах нет.
- Вход: `auth/?phone=…&password=…`. Сервер сам вычисляет SHA-1 пароля и возвращает `{token, kkt}`. Значение `token` имеет форму `login:passwordHash`; в остальных запросах оно передается параметром `token`, а не `Authorization: Bearer`. Источник: [auth/index.php](../../b2b/auth/index.php), строки 6–31; [catalog/index.php](../../b2b/catalog/index.php), строки 6–19.
- CORS у большинства обработчиков: origin `*`, методы `GET, POST`, разрешенный дополнительный заголовок только `X-Requested-With`. Отдельного обработчика `OPTIONS` нет. Для совместимости клиенту не нужны `Content-Type: application/json`, `Authorization`, cookies или другие нестандартные заголовки.
- Числа в товарных объектах преимущественно сериализуются **строками**, флаги могут быть строками `"0"` / `"1"`, числом `0` либо пустой строкой. `Boolean("0")` не подходит для разбора. Поля коллекций иногда содержат `null` из-за неинициализированной PHP-переменной.
- Успешные ответы различаются: JSON-объект, JSON-строка, текст, JSON `null` и полностью пустое тело. У ряда JSON-ответов отсутствует `Content-Type: application/json`; парсить нужно согласно контракту маршрута, а не только заголовку.
- Невалидный токен обычно возвращает **400**, не 401. Тело нередко `null` или пустое; у входа возвращается русский текст. Любой 400 нельзя безусловно считать истекшей сессией: например, `search/barcode/` возвращает 400 и при ненайденном штрихкоде.
- Мутации тоже GET, поэтому их нельзя предварительно загружать, автоматически повторять или кешировать. После изменения корзины необходимо читать `cart/` заново: сервер пересчитывает цены и бонусы.

### Форматы товаров

```ts
type Category = { id: string; name: string; image: string; parent: string };
type Tag = { vid: string };
type ProductImage = { id: string | number; href: string };

// Сырые данные PHP. Отдельные необязательные поля отсутствуют в разных маршрутах.
type Product = {
  id: string;
  name: string;
  image: string;
  price: string;       // цена продаваемой упаковки / единицы заказа
  ratio: string;       // число базовых единиц в упаковке
  price_one: string;   // price / ratio
  ediz?: string;       // сокращение названия единицы до 2 символов
  opt?: string;       // альтернативная цена для товара с характеристикой
  opt_one?: string;   // альтернативная цена за базовую единицу
  aid?: string | number;
  aprice?: string | number;
  mark?: string | number;
  bonus?: string;
};

type ProductDetail = Omit<Product, 'image'> & { back: string };
```

Источники полей: [catalog/index.php](../../b2b/catalog/index.php), строки 48–51, 93, 149–173, 202–213; [catalog/id/index.php](../../b2b/catalog/id/index.php), строки 64–71, 83–94, 121–130; [catalog/act/index.php](../../b2b/catalog/act/index.php), строки 95–107.

`aid` — идентификатор акции; `aprice` — цена из таблицы `action`, которая применяется сервером при выполнении условий состава заказа. Наличие `aid` не означает, что можно безусловно заменить обычную цену на `aprice`. `bonus` в карточке — процент, а `bonus` в ответе корзины — вычисленная сумма. `mark` обозначает маркировку; в `catalog/id/` он, однако, принудительно строится из признака `har`, что может отличаться от списка.

Товарный API не возвращает рейтинг, отзывы, бренд, описание, артикул, дату новизны, список характеристик, полную категорийную цепочку или точный доступный остаток. `tags` не сопоставлены отдельным товарам: `vid` отсутствует внутри `Product`. Поэтому фильтрацию карточек по этим тегам нельзя достоверно реализовать по ответу. Сервер выбирает первую доступную характеристику автоматически; query-параметра выбора варианта нет.

В API отсутствуют `page`, `limit`, `sort`, `min_price`, `max_price` и брендовые фильтры. Сортировку и фильтр цены можно применять локально к уже полученному набору, не выдавая его за весь каталог. Корневой `catalog/` не является выгрузкой всех товаров. Новинки существуют только как `home.new.products` — выборка максимум 25 последних по внутреннему ID немаркированных товаров; отдельного `/new/` и признака `isNew` в товарах нет.

```ts
type CartLine = {
  id: string; name: string; image: string;
  price: string; // СУММА СТРОКИ, уже умноженная на count
  count: string;
  ediz: string;
  action: string | number;
  aprice?: number;
  discount: string;
};
```

Цена `CartLine.price` уже равна стоимости всей строки: [cart/index.php](../../b2b/cart/index.php), строки 104–115, 124–135, 143–153, 224–242. Нельзя повторно умножать ее на `count`. Для справочного отображения цены одной единицы заказа допустимо делить сумму строки на количество. Итоги берутся из `amount` и `bonus`, а не пересчитываются по ценам каталога.

Один товар может присутствовать в ответе дважды: строка с акцией и строка без акции имеют одинаковый `id`, но разные `action`, `count` и `price` (строки 104–140). Их нельзя молча потерять при преобразовании в словарь по `id`; количество товара для бейджа суммируется, а строки отображаются раздельно либо объединяются с сохранением общей суммы.

`count` — количество единиц заказа; `ratio` не является обязательным шагом изменения корзины. Сервер перемножает цену упаковки на `count` и сам выбирает характеристику и тип цены. Для формы количества на клиенте разумны положительные целые числа; проверки положительности и доступного остатка у мутации на сервере отсутствуют.

### Что означает `chz` в коде

В [cart/index.php](../../b2b/cart/index.php), строки 14–18, читается существующий `users.discount`. Строки 258–265 вычисляют:

```text
razn = round(розничная сумма товаров с характеристикой × 0.04, 2)
chz ответа = существующий users.discount + razn
```

В [cart/clouse/index.php](../../b2b/cart/clouse/index.php), строка 36, выполняется:

```text
users.discount = users.discount + chz из запроса
```

Следовательно, параметр оформления — **приращение баланса**. Передавать полный `cart.chz` ошибочно: существующий баланс прибавится повторно. Для начисления суммы текущей корзины по этому алгоритму используется `cart.razn`; `chz=0` ничего не начисляет. Само бизнес-название и условия начисления из исходников однозначно не восстанавливаются. Это не параметр скидки, которую клиент вправе вычитать из `amount`. Клиент не должен создавать собственные правила применения «ЧЗ».

Оформление не обновляет `orders.sum`: оно меняет статус, комментарий и баланс. Расчет `orders.sum` при мутациях и отображаемый `cart.amount` могут расходиться из-за пересчета акций. Нет транзакций и ключа идемпотентности: автоматические повторы оформления и параллельные мутации нежелательны. Успех оформления подтверждается непустым `order_id`.

## Ограничения существующего сервера

Следующие проблемы зафиксированы по коду; PHP-файлы, окружение и БД в рамках задачи не менялись.

1. **Отсутствуют зависимости окружения.** В рабочей папке не представлены `conf/db.php` и `conf/tb.php`, которые подключаются относительными путями за пределами `b2b`. Соединения `$db` / `$tb` и схема таблиц не определены в переданном коде. Без них проверка реальных ответов невозможна. Например, [catalog/index.php](../../b2b/catalog/index.php):8; [setting/setupKassa/index.php](../../b2b/setting/setupKassa/index.php):8–9.
2. **Требования совместимости PHP.** Почти все файлы начинаются с короткого `<?`, то есть зависят от настройки `short_open_tag`. Есть неинициализированные массивы и арифметические операнды, потенциально приводящие к предупреждениям или ошибкам на современных PHP: `in_array($vid, $test)` без инициализации `$test` в [catalog/id/index.php](../../b2b/catalog/id/index.php):157; `array_sum($bon/$roznn/$optt/$summm)` без гарантии массивов в [cart/index.php](../../b2b/cart/index.php):257–261; деление на отсутствующий `$prod_ratio` там же:212, 219, 226. Обработчик избранного содержит `fopen(log.log, "a")` без кавычек: [favorite/add/index.php](../../b2b/favorite/add/index.php):7. Точную совместимость без запуска не подтверждали.
3. **Неполные ответы и отсутствие 404.** Карточка не проверяет, найден ли товар, прежде чем вычислять цену и создавать объект: [catalog/id/index.php](../../b2b/catalog/id/index.php):24–44, 117–130. Клиенту нельзя считать любой объект с запрошенным `id` валидным товаром. Пустые/невалидные цены и имя требуют обработки. Коллекции `null` можно нормализовать в `[]`, но HTML-ошибку PHP или сломанный JSON нельзя показывать как успешно загруженный пустой каталог.
4. **Жестко заданные хосты изображений.** Список каталога использует `https://21baza.ru`, карточка и поиск — `https://new.21baza.ru`. Примеры: [catalog/index.php](../../b2b/catalog/index.php):42, 106–110; [catalog/id/index.php](../../b2b/catalog/id/index.php):65–71; [search/index.php](../../b2b/search/index.php):105–109. Настройка базового URL API не меняет эти ссылки. При недоступности изображения клиент должен показывать локальную заглушку.
5. **Неполные функции.** Избранное не сохраняется; отзывы/рейтинги и серверные фильтры отсутствуют. `home.hit` выбирает случайные товары, а не продажи; `home.new` — последние внутренние ID, без дат. [home/index.php](../../b2b/home/index.php):44, 102.
6. **Учетные данные в query.** Пароль входа и токен передаются в URL согласно существующему контракту. Не нужно добавлять их в сообщения ошибок, аналитику и консоль. Сервер сам пишет `$_GET` в лог в [top/index.php](../../b2b/top/index.php):6–9 и [favorite/add/index.php](../../b2b/favorite/add/index.php):6–9. Содержимое логов в аудите не читалось.
7. **SQL и права доступа.** Параметры напрямую интерполируются в SQL, без prepared statements. Некоторые обработчики аутентифицируют пользователя, но не проверяют принадлежность запрошенной записи: [history/id/index.php](../../b2b/history/id/index.php):25, 32; [edo/id/index.php](../../b2b/edo/id/index.php):22, 30; [geo/index.php](../../b2b/geo/index.php):27. Клиентская валидация не устраняет эти серверные ограничения.
8. **Мутации неидемпотентны.** Добавление товара, начисление `chz`, заказ/отмена подарка, прием ЭДО меняют состояние без ключа операции и транзакции. При сетевой неопределенности сначала нужно перечитать состояние, а не автоматически повторять GET-мутацию.

## Проверка интеграции после подключения окружения

Запуск и подключение PHP/БД остаются отдельной задачей. Когда готовый API будет доступен, достаточно проверить: вход и неверный пароль; корневые и вложенные группы; поиск, включая пустой результат; карточку и акцию; добавление двух единиц, уменьшение на одну и удаление; две строки одного акционного товара; пустую корзину; одно оформление с валидным `order_id`; недоступное изображение и ошибку сервера. До этого корректность фронтенда проверяется сборкой и тестами HTTP-контракта с контролируемыми ответами без обращения к PHP.
